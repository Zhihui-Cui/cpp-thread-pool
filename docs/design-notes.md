## Issue #1：泛型线程安全任务队列

[查看 Issue](https://github.com/Zhihui-Cui/cpp-thread-pool/issues/1)

### 学习范围与文件

- 学习范围：mutex、lock_guard、模板、optional；实现安全存取与边界情况测试。
- 文件位置：`include/task_queue.hpp`、`tests/task_queue_test.cpp`

### 已有设计记录

- `push()`、`try_pop()`、`empty()` 使用同一个成员互斥量 `mutex_`。
- `try_pop()` 的判空、取值、删除在一次持锁期间完成。
- `lock_guard` 离开作用域时自动解锁，包括提前 `return` 的情况。
- 空队列返回 `std::nullopt`。
- `empty()` 只反映检查那一刻的状态。

### 我的理解与设计选择

- 判空和出队必须在同一次持锁操作中完成。如果中间释放锁，其他线程可能取走最后一个元素，之前的“非空”判断就失效了。这里讨论的是同一进程内的多个线程。
- 模板实现放在头文件中，不只是为了复用：编译器根据 `ThreadSafeQueue<int>`、`ThreadSafeQueue<std::string>` 等具体类型生成代码时，通常需要看到模板定义。本项目没有采用显式实例化，因此将声明和实现一起放在头文件中。
- `0` 是一个有效的元素值，不能用它代表“没取到任务”。`std::optional<T>` 分别表达“有一个值”和“没有值”，空队列返回 `std::nullopt`。
- `auto` 在声明时推导类型，之后类型不再变化。整数队列的取出结果是 `std::optional<int>`，即使结果为空也仍是这个类型；字符串结果使用单独的变量。
- `push(T task)` 按值接收参数。传入普通字符串变量时，先复制出参数 `task`，再通过 `std::move(task)` 允许队列移走参数的资源，避免再复制一次。`std::move` 本身不搬运数据，实际是否移动以及如何移动取决于类型；对于整数，移动通常没有额外收益。
- `empty()` 只描述检查那一刻的状态，因此调用方应直接根据 `try_pop()` 的结果决定是否使用元素，而不是先调用 `empty()` 来保证随后一定能取到。

### 遇到的问题与解决过程

以下为 Issue #1 学习过程中实际遇到的问题。

- **`std` 中找不到 `mutex`**：补上 `<mutex>` 后仍报错，修改编辑器的 C++17 设置也未解决。直接用编译器检查发现，旧工具链是 GCC 7.3.0 的 `win32` 线程模型，该安装无法编译 `std::mutex`。改用 MSYS2 UCRT64 GCC，并更新编辑器的编译器路径；新版 GCC 的语法检查和后续构建通过。
- **PowerShell 找不到 `g++`**：编辑器的 `compilerPath` 和终端的 `Path` 是不同配置。先用完整路径执行编译器，再将 `C:\msys64\ucrt64\bin` 加入用户 `Path`，重启 VS Code 后验证。最终能直接运行 `g++` 命令。
- **直接编译头文件时出现 `#pragma once` 警告**：头文件被当成主编译文件，导致用途提醒。保留 `#pragma once`，改由测试 `.cpp` 包含头文件并编译；该警告不需要通过删除头文件保护来解决。
- **不会创建 `lock_guard` 对象**：最初只写了类型 `std::lock_guard<std::mutex>;`，没有创建对象或指定互斥量。改为 `std::lock_guard<std::mutex> lock(mutex_);`，让局部对象从构造时加锁，直到离开作用域时解锁。后续构建通过。
- **`empty() const` 中加锁时报参数为 `const std::mutex`**：加锁会改变互斥量的内部状态，而 `const` 成员函数默认不能修改普通成员。将锁声明为 `mutable std::mutex mutex_;`，保留 `empty()` 的 `const`。锁状态可以变化，但队列的逻辑内容不变；修改后编译通过。
- **CMake 的 Ninja 与 MinGW Makefiles 冲突**：原 `build/` 缓存了另一种生成器配置。改用独立的 `build-ninja/`，明确指定新版 GCC、Ninja 和 Debug；配置输出 `Found Threads: TRUE`、`Configuring done`、`Generating done`，随后编译和 CTest 通过。

## Issue #2：单线程任务执行器

[查看 Issue](https://github.com/Zhihui-Cui/cpp-thread-pool/issues/2)

### 学习范围与文件

- 学习范围：lambda、捕获、`std::function`、移动语义；提交并按顺序执行任务；头文件与源文件分工、测试组织和 CMake 目标注册。
- 文件位置：`include/single_thread_executor.hpp`、`src/single_thread_executor.cpp`、`tests/single_thread_executor_test.cpp`、`tests/task_queue_test.cpp`、`CMakeLists.txt`；说明与总结写在 `README.md`、`docs/design-notes.md`。

### 我的理解与设计选择

- **保存任务与执行任务是两个动作**：lambda 可以像普通对象一样放进队列。`submit()` 只保存任务，函数体中的赋值或追加元素此时不会执行。`run()` 才负责反复取出任务并调用，直到队列为空。当前执行器不创建新线程，任务在调用 `run()` 的线程中执行。
- **任务需要统一的存储类型**：不同 lambda 有不同类型，`std::function<void()>` 可以包装符合“无参数、无返回值”调用形式的可调用对象，让这些任务进入同一个 `ThreadSafeQueue<std::function<void()>>`。
- **取出不等于调用**：`try_pop()` 将任务从队列移除，并返回包含任务的 `optional`。`has_value()` 检查是否取到任务，`task.value()` 取得函数对象，后面的 `()` 才调用函数。因此 `task.value()()` 才会产生任务中的效果；队列变空可能发生在任务执行之前。
- **捕获决定任务使用哪个数据**：`[&value]` 通过引用访问外部的 `value`；`[&order, i]` 让多个任务访问同一个 `order`，同时让每个任务保存提交时的 `i` 副本。引用捕获的对象必须在任务执行时仍然存活。本阶段的测试在局部变量离开作用域前调用 `run()`。
- **提交时移动任务对象**：`submit(std::function<void()> task)` 按值接收任务，再用 `tasks_.push(std::move(task))` 将参数交给队列。`std::move` 允许后续操作使用移动语义，它本身不会执行任务。
- **封装的目的**：把测试中重复的“入队、循环取出、调用”收进 `SingleThreadExecutor`。调用方使用 `submit()` 和 `run()`，不必自己写取任务循环。`try_pop()` 返回时内部的锁已经释放，调用任务发生在队列锁之外。
- **文件按组件和职责组织**：执行器是普通类，在 `.hpp` 中声明、`.cpp` 中实现。Issue #1 的队列是模板，当前组织方式要求使用它的代码能看到模板定义，因此实现留在头文件中，不需要补建 `task_queue.cpp`。
- **测试按行为拆分**：队列测试验证存取和可调用对象的保存；执行器测试验证延迟执行、顺序执行和不重复执行。每个测试函数创建自己的对象，`main()` 只组织调用，避免测试之间依赖同一个队列的残留状态。
- **CMake 描述构建关系**：将执行器源文件加入 `thread_pool` 库；用 `add_executable` 创建测试程序、`target_link_libraries` 链接库、`add_test` 注册测试。终端中的配置、构建和测试是不同步骤，`ctest` 不会重新编译修改后的代码。

### 遇到的问题与解决过程

- **`value == 42` 断言失败**：最初只写了 `task.value();`，取到函数对象却没有调用它，所以 `value` 仍为初始化的 `0`。改成 `task.value()();`，重新编译和测试后通过。由此理解“保存、取出、执行”是三个不同操作。
- **测试不断堆进一个 main**：最初整数、字符串、lambda 和顺序执行练习都写在队列测试中。整理时把队列测试拆成六个独立函数，执行器测试拆成两个独立函数，并去掉队列测试中重复的三个 lambda 顺序执行练习。整理后两个测试程序均通过。

## Issue #3：多 worker 生命周期管理

[查看 Issue](https://github.com/Zhihui-Cui/cpp-thread-pool/issues/3)

### 学习范围与文件

- 学习范围：`std::thread`、共享队列、`join()`、停止状态与作用域；指定 worker 数并正确完成 1,000 个任务；补充 `explicit`、函数包装、异常捕获与重新抛出、构建链接和代码风格。
- 主要文件：`include/thread_pool.hpp`、`src/thread_pool.cpp`、`tests/thread_pool_test.cpp`、`CMakeLists.txt`；文档和格式约定见下方归档记录。

### 我的理解与设计选择

以下内容依据本阶段本人在对话中的复述整理，并保留纠正后的表述；不把经过提示后能够解释等同于已经能独立重写全部代码。

- **主线程创建 worker，新线程执行入口函数**：`workers_` 是存放 `std::thread` 对象的容器，不是一个线程。`emplace_back([this] { worker_loop(); })` 在容器中构造线程对象，由新线程调用 lambda，再进入当前线程池对象的 `worker_loop()`。主线程不等待这个循环结束，因此可以继续创建其他 worker，并在构造函数返回后提交任务。直接调用 `worker_loop()` 则仍在当前线程中执行，不会自动创建线程。

- **提交和执行由不同代码负责**：`submit()` 把任务移入 `tasks_`；worker 从队列取出函数对象，调用 `task.value()()` 才执行任务。后台线程已启动，任务可能在 `submit()` 返回前开始执行。
- **函数包装描述调用方式**：`std::function<void()>` 表示无参数、调用时不提供返回值的形式。`std::function<int()>` 可返回整数，但 worker 拿到结果不等于主线程自动得到结果；当前 `submit()` 返回 `void`，跨线程获取结果留到 Issue #5。`explicit` 限制整数隐式转换为线程池对象，仍允许 `ThreadPool pool(4)` 这样的直接构造。
- **两把成员锁各有职责**：队列的 `mutex_` 保护判空、取出和删除；线程池的 `state_mutex_` 保护 `stopping_` 的访问，当前实现还将取任务放在这一临界区中。队列锁在 `try_pop()` 返回时释放，状态锁在内部作用域结束时释放。调用任务时不持有这两把锁。外层状态锁目前也串行化了 worker 的取任务过程，是本阶段便于理解的保守实现。
- **任务自身的共享数据另行保护**：队列安全不等于任务修改的数据也安全。多个 worker 执行 `++count` 时，要使用同一把锁；各自创建一把锁不能形成互斥。测试使用 `result_mutex` 保护 `hits`，每个任务按值捕获自己的编号 `i`，引用捕获的结果容器和锁必须存活到任务结束。
- **空队列不等于任务完成**：一个 worker 可能已经取走最后的任务但还在执行。取不到任务且 `stopping_ == false` 时继续轮询；取不到任务且 `stopping_ == true` 时才退出。即使已请求停止，取到了任务仍先执行。`yield()` 只是建议调度器给其他线程执行机会，返回后继续检查，不是睡到新任务到来，也不保证一定切换线程。
- **析构先通知，再等待**：当前用法中主线程执行析构函数，加锁设置 `stopping_ = true`，解锁后逐个 join。若持锁 join，worker 无法取得同一把锁来检查退出条件，双方可能互相等待。`join()` 等待线程结束，不启动线程，也不强制中断正在执行的任务。
- **构造失败需要就地清理**：第三个 worker 创建失败时，前两个可能已经运行，但整个线程池尚未构造成功。构造函数抛出异常时不会调用 `~ThreadPool()`；已构造好的成员仍会被销毁。因此构造函数的 `catch (...)` 先设置停止状态、解锁、join 已创建的线程，再用 `throw;` 保留并重新抛出原异常。如果捕获后清理但不重新抛出，构造函数会正常结束，对象会被视为构造成功，却没有仍在工作的 worker；容器中可能还保留已经 join 的线程对象。不能简单说成“对象没有创建”。

## Issue #4：阻塞等待与唤醒

[查看 Issue](https://github.com/Zhihui-Cui/cpp-thread-pool/issues/4)

### 学习范围与文件

- 学习范围：condition_variable、unique_lock、等待谓词、虚假唤醒。
- 文件位置：`include/thread_pool.hpp`、`src/thread_pool.cpp`、`tests/thread_pool_test.cpp`；文档为 `README.md` 和本文件。沿用已有队列接口。

### 我的理解与设计选择

以下内容依据本阶段本人在对话中的复述与追问整理，并保留纠正后的表述；在提示下完成实现和解释，不等于已经能够独立重写全部代码。

- **从轮询改为阻塞等待**：原来的 worker 在没有任务时调用 `yield()`，随后继续循环检查队列，仍然消耗 CPU 执行这些检查。改用带谓词的 `wait()` 后，worker 在队列为空且没有停止请求时释放锁并阻塞等待。被唤醒后，它重新取得锁并检查状态，再决定继续等待、取任务或退出。`wait()` 刚被调用时也会先检查谓词，条件成立便直接返回，不必先等待一次通知。
- **对象和执行线程的区别**：`cv_` 是线程池的条件变量成员，不是线程，也不会自己执行代码。worker 调用 `cv_.wait()`，等待的就是该 worker；提交线程调用 `cv_.notify_one()`。测试里的 `result_cv` 是另一个对象，由主线程等待、任务通知；它与线程池内部的 `cv_` 各自管理等待者。
- **锁与等待的顺序**：`unique_lock` 创建时取得 `state_mutex_`。`wait()` 在持锁状态下检查谓词；为假时原子地解锁并进入等待；醒来后先重新取得锁，再检查谓词。等待期间局部 `lock` 对象仍存在，但不持锁。谓词为真时 `wait()` 返回，仍持有锁；取任务后离开内部作用域，再执行任务。
- **为什么传匿名函数**：直接传 `stopping_ || !tasks_.empty()` 只会先计算出一个 `bool`，不符合谓词需要可调用对象的接口要求。lambda 可供 `wait()` 在进入等待前、每次醒来后重新调用。lambda 的 `return` 把判断结果交给 `wait()`，不会退出 `worker_loop()`；一次带谓词的 `wait()` 调用内部可以反复等待和判断，直到条件成立。
- **结束等待与退出不同**：谓词 `stopping_ || !tasks_.empty()` 表示有任务或需要处理停止请求。即使已经停止，取到任务仍先执行；只有 `!task.has_value() && stopping_` 成立才退出循环。停止请求不强制中断正在执行的任务。
- **两把锁的配合**：提交线程也会通过 `tasks_.push()` 使用队列内部的锁，但这把锁只保护单次队列操作，不能覆盖检查条件到进入等待的配合过程。因此 `submit()` 还取得 `state_mutex_`，入队、解锁后通知；worker 使用同一把外层锁检查条件并等待。这样避免任务在检查为空后、进入等待前入队并发出无法保留的通知。当前需要两把锁时，顺序均为先状态锁、再队列锁。
- **通知不分配任务**：`notify_one()` 通知同一条件变量上的一个等待线程，不保证先等待者先被唤醒，也不把锁或任务交给它。另一个正在执行旧任务的 worker 可能先回到循环、取得锁并取走新任务。虚假唤醒时也未必有任务，所以醒来后必须重新检查谓词。接口规则参考 [C++ 标准草案](https://eel.is/c++draft/thread.condition.condvar)。
- **停止时先解锁、通知，再 join**：析构和构造失败清理都先在锁内设置 `stopping_`，解锁后 `notify_all()`，再逐个 `join()`。先 join 可能使通知无法执行；持锁 join 会让 worker 无法取得锁检查退出条件；只通知一个可能留下其他等待者。`join()` 只等待结束，不负责唤醒或停止线程。
- **异常处理需要自己编写**：`try` 中调用的标准库操作也可能抛出异常。`catch (...)` 捕获从对应 try 块传播出的各种 C++ 异常，清理动作由自己编写；它不会捕获另一个 worker 线程执行任务时抛出的异常。构造失败时已创建的 worker 不会自动结束，清理后用 `throw;` 重新抛出原异常，向调用方报告失败；不能清理完就把构造当作成功。
- **析构前检查与重复测试**：析构本身会通知 worker，只在析构后检查结果，无法区分任务是否依靠析构通知才执行。新测试在同一个单 worker 池存活期间执行三轮，每轮加锁重置 `completed`、提交任务，再由主线程使用带谓词的 `wait_for()` 等待标记并断言。任务加锁设置标记、解锁后通知；若不重置，上一轮的 `true` 可能使下一轮直接通过。两秒是等待时限，条件满足可提前返回；等待返回的 `bool` 表示最后的谓词判断结果。

### 遇到的问题与解决过程


- **把通知写在 join 后面**：析构和构造函数 catch 中最初均将 `notify_all()` 放在 join 循环后。代码检查发现等待中的 worker 可能无法退出，主线程也就执行不到通知。将通知移到解锁之后、join 之前，再构建和运行测试通过；没有把错误版本运行挂住当作已发生的测试结果。
- **旧的 yield 分支未删除**：第一次加入等待后仍保留原来的 else/yield，检查后删除，统一由谓词等待处理空闲状态。
- **重置完成标记时遗漏锁**：三轮测试最初直接写 `completed = false`，之后补上独立的 `lock_guard` 作用域，并保留声明时初始化。当前成功等待后上一轮已完成对标记的写入，不能直接把原写法断言为数据竞争；统一加锁使共享状态访问规则更明确。
