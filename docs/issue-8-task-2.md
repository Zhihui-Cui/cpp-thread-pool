## 1. 锁的作用域与任务的作用域不同

worker 每轮先声明一个 optional 任务变量，再进入内部大括号取得状态锁。等待、取出任务和检查退出条件都放在这段锁内；退出内部大括号后调用任务。

```text
本轮循环开始：task 创建
  内部作用域开始：lock 创建并持锁
    wait：等待时释放锁，返回前重新获得锁
    取任务
    没取到任务且已停止：退出 worker
  内部作用域结束：lock 销毁并解锁
  调用 task 中的可调用对象
本轮循环结束：task 销毁
```

将 task 放在锁外声明，是为了让它在解锁后仍然存在，并不意味着读取共享队列时不加锁。这里 task 是 worker 自己的局部对象；共享的是任务队列和停止状态。

最新一版用户代码已经修复了 stopping_ 在锁外读取的问题。try_pop 单独放在状态锁外时，队列自身仍有锁保护，而且代码检查了 optional，所以不能把它本身说成必然产生数据竞争。此次把出队也放回状态锁内，是为了让“检查条件—取任务—决定退出”的过程统一，便于理解和维护。

状态锁与队列内部锁职责不同：前者协调停止、提交和等待；后者保护队列容器。当前调用顺序是先状态锁、再队列内部锁，没有相反的获取顺序。

## 2. 构造失败为什么不能依赖析构函数

正常构造完成后，析构函数可以调用 stop 回收线程。但如果构造函数中途抛异常，整个 MinimalThreadPool 尚未构造成功，它的析构函数不会执行，已经构造完成的成员仍会被销毁。

假设已经启动两个 worker，创建第三个时失败：直接让异常离开构造函数会开始销毁成员，而前两个 worker 可能还在访问这些成员；含有 joinable 线程的 std::thread 被销毁也会导致 terminate。

因此在线程创建循环外使用 try/catch：

1. catch (...) 捕获创建过程中的任意异常。
2. 调用 stop：持锁设置停止状态，解锁后通知所有 worker，并逐一 join。
3. 使用 throw; 重新抛出原异常，让调用者知道构造失败。

这里复用 stop，是因为进入构造函数体时所需成员已经初始化，且不会有外部线程同时调用 stop。

正常析构也只调用一次 stop。用户新增的第二段 join 循环在 stop 已完成回收后只是冗余检查，也不能修复构造失败路径。

## 3. 异常测试必须检查“没有抛异常”的路径

正确的异常测试先将 caught 设为 false，仅在捕获到预期类型时设为 true，最后 assert(caught)。

- 抛出预期异常：标记为 true，测试通过。
- 没有抛出异常：标记仍为 false，断言失败。
- 抛出其他类型：不会被该 catch 吞掉，测试程序失败。

只写一个空 catch，会遗漏“应该拒绝却接受了”的错误。零 worker 应捕获 invalid_argument，停止后提交应捕获 runtime_error。

## 4. 如何证明析构等待了任务

结果变量与保护它的 mutex 放在线程池所在的内部作用域之外。多个任务在锁内更新结果，离开池的作用域时析构调用 stop，等待所有 worker 结束，然后再检查结果。

这里有两种不同的同步需求：任务之间同时写入，需要 mutex；主线程在 join 全部结束后读取，不再与任务并发，因此不必为了这次读取再加锁。

任务写 return 1 无法证明执行过，因为 std::function<void()> 会丢弃该返回值。测试必须观察完成计数等实际效果。

## 5. 新增测试为什么让任务再次 submit

测试仅用一个 worker，外层任务提交内层任务后返回；内层任务设置完成标志并通知测试线程。

如果 worker 调用外层任务时仍持有 state_mutex_，内层 submit 就会试图再次取得这把锁，测试无法完成。因此它针对的是“执行用户任务前释放内部锁”这个要求，同时检查池在 stop 之前就会执行任务。

主线程用条件变量等待完成，最多等待 5 秒；等待成功后才 stop，避免把关闭与内部提交的竞争引入本测试。外层任务不能等待内层任务完成：唯一的 worker 还在外层任务中，内层任务就无法得到执行机会。
