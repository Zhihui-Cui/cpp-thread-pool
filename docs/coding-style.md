# 本项目的代码风格

代码首先要正确，其次要方便别人理解和修改。排版没有所有公司通用的唯一答案；进入一个项目时优先遵守它现有的约定。本项目采用以下规则，减少写代码时反复纠结格式的时间。

## 自动格式化

- 根目录 `.clang-format` 统一 C++ 排版；当前已使用 clang-format 22.1.3 验证配置。
- 本机 VS Code 的 C/C++ 扩展已配置 C++ 保存时格式化，也可在命令面板执行“格式化文档”。本地 `.vscode/settings.json` 按已有规则不提交。
- `.editorconfig` 声明 UTF-8、LF 换行、4 空格缩进和文件末尾换行，供支持 EditorConfig 的编辑器使用。
- `.gitattributes` 让 Git 检出源码和项目配置时也使用 LF，避免 Windows 的默认换行转换与编辑器约定冲突。
- clang-format 负责 C++ 空格、缩进、折行等机械规则，不负责 CMake 排版，也不能替你判断所有逻辑段落。
- 本项目启用 `InsertBraces`：格式化会为适用的控制语句补大括号。格式化后仍应检查差异，尤其是宏或复杂语法附近。

## 缩进和大括号

每层使用 4 个空格，不混用 Tab。函数、类、控制语句的左大括号放在同一行，函数体和控制语句体展开书写。`namespace` 内不额外缩进，类的 `public:`、`private:` 与 `class` 对齐，成员缩进一层。

即使只有一句，`if`、`else`、`for`、`while` 也使用大括号：

```cpp
if (!task.has_value() && stopping_) {
    return;
}

if (task.has_value()) {
    task.value()();
} else {
    std::this_thread::yield();
}
```

`else` 和 `catch` 接在前一个右大括号的同一行，例如 `} catch (...) {`。不要用缩进冒充真正的作用域，也不要为了少一行把控制条件和执行动作挤在一起。

## 空格

| 位置 | 本项目写法 |
| --- | --- |
| 控制关键字与左括号之间 | `if (ready)`、`for (...)`、`catch (...)` |
| 函数名与左括号之间 | `submit(task)`、`worker.join()`，不加空格 |
| 二元运算符两侧 | `count = 0`、`i < 4`、`i *= 2`、`a && b` |
| 逗号后 | `[&hits, &mutex, i]` |
| 范围 for 的冒号两侧 | `for (auto& worker : workers_)` |
| 引用和指针 | `auto& worker`、`const T& value`、`T* pointer` |
| lambda 捕获列表与函数体之间 | `[this] {` |
| 一元运算符与操作数之间 | `++i`、`!ready`，不加空格 |

`auto& worker` 和 `auto &worker` 在语法上相同；这里选择前者以保持一致。

## 空行：按逻辑分段

把函数当作一小段说明文：一个连续的小步骤放在一起，进入下一个步骤时空一行。通常只空一行，不连续空多行，也不在每条语句后空一行。

适合空一行的地方：

- 两个函数定义之间。
- 头文件包含组之间。
- 参数检查结束，开始主要流程之前。
- 准备测试数据、执行操作、检查结果这几个阶段之间。
- 锁的作用域结束，开始执行任务或 join 之前。
- 同一函数内两个目的不同的代码段之间。

通常保持连续的地方：

- 同组变量声明、同组成员声明。
- 一个操作及其紧接着的检查。
- 多条针对同一个结果的断言。
- 注释和它解释的代码之间。

空行不改变程序语义；大括号可能改变变量和锁的生命周期。例如：

```cpp
{
    std::lock_guard<std::mutex> lock(state_mutex_);
    stopping_ = true;
}

for (auto& worker : workers_) {
    worker.join();
}
```

中间的空行帮助读者区分“通知停止”和“等待结束”；真正使锁提前释放的是内部大括号。

## 文件组织与长行

- `.cpp` 优先包含对应组件的头文件，再空一行放标准库头文件，之后放其他项目头文件；组内排序交给格式化器。
- `.hpp` 开头是 `#pragma once`，再分组包含头文件。直接使用标准库类型时，显式包含它对应的头文件。
- 每行以 100 列作为格式化上限；长参数列表和表达式由工具折行，不靠大量空格手工对齐。
- 一个文件只使用一种排版。CMake 沿用 4 空格缩进，每个测试的创建、链接、注册放在同一组，不同测试之间空一行。
- 文件末尾保留换行，删除无意义的行尾空格。

## 比排版更重要的习惯

- 命名说明用途：沿用 `ThreadPool`、`worker_loop()`、成员后缀 `_` 等现有风格。
- 一个函数承担清晰的职责；不要为了格式化顺便改变执行顺序、变量作用域或锁的范围。
- 注释解释原因和约束，例如“join 前释放状态锁”，避免只把语句翻译一遍。
- 测试函数写完要在 `main()` 中调用；新增测试程序还要注册到 CMake。
- 修改后先保存并检查差异，再构建、运行测试。格式整齐不等于逻辑正确。
