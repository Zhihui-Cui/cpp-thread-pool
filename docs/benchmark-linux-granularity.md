# Linux 串行基线与任务粒度实验

日期：2026-09-30。此次为 #9 之后的性能学习实验，不扩展线程池功能。

## 目的与环境

比较主线程直接计算与 1/2/4 worker 线程池执行同一批任务的耗时，观察任务计算量改变后的收益和波动。

- 环境：WSL Ubuntu 24.04、GCC 13.3.0、CMake 3.28.3、Ninja、C++17。
- 构建：`out/linux-release`，助手核对 CMake 缓存及 Ninja 参数为 Release、`-O3 -DNDEBUG`。
- 任务：每批 1000 个任务，seed 为 1～1000；每任务分别执行 100000 轮或 1000 轮整数计算。
- 两种粒度通过修改 `main()` 中的 `iterations` 并重新构建分别测量；当前源码保留 `iterations = 1000`，不支持命令行切换粒度。
- 运行由本人完成并提供输出。助手核对源码、构建配置和两份复测日志，计算加速比、整理记录，没有代跑本次性能测量。

## 方法与复现

```bash
cmake -S . -B out/linux-release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build out/linux-release --target thread_pool_benchmark -j 2
./out/linux-release/thread_pool_benchmark
```

复现重任务组时，将 `benchmarks/thread_pool_benchmark.cpp` 中的 `iterations` 改为 `100000`，保存并重新构建后运行；轻任务组使用 `1000`。任务数量及 seed 范围保持不变。轻任务总计算量也是重任务的 1/100，本实验不是总计算量固定的任务拆分实验。

直接串行使用 `run_serial_benchmark()`，在主线程循环调用 `compute_task()` 并累加 checksum。线程池版本使用已有 `run_benchmark()`，提交任务并通过 future 收集结果。计时均使用 `steady_clock`，串行计时包含循环计算及累加；线程池计时包含提交、包装、入队、执行及结果收集，不包含池构造、future 容器预留、池关闭及输出。

每种执行方式先预热一次，再正式测量五次，排序取中位数。线程池每次调用创建新池；预热不意味着后续测量复用已就绪的 worker。虽然池构造在计时前，仍未设置 worker 全部就绪的屏障。测量顺序固定为串行、1/2/4 worker，未随机化。

每次运行在计时外生成 `expected_checksum`，预热及每次正式测量均用 `if` 检查结果，Release 下仍有效。输出在各次计时区间外。checksum 一致是结果校验，不构成对所有并发行为的证明。

轻任务首次结果中 4 workers 波动较大，保持代码和参数不变，按提示再测两次：

```bash
./out/linux-release/thread_pool_benchmark | tee out/linux-release/light-repeat-1.txt
./out/linux-release/thread_pool_benchmark | tee out/linux-release/light-repeat-2.txt
```

两份文件位于被 Git 忽略的 `out/` 中；下表保留所有正式测量数据，避免后续清理构建目录丢失证据。首次重任务、首次轻任务来自聊天中的原始输出；复测数据另与上述文件核对一致。预热只作校验，没有输出耗时；未记录 pipeline 中 benchmark 进程的独立退出码，不以 `tee` 的状态充当该进程退出状态。

## 观察与解释边界

- 重任务这一批中，2/4 workers 比直接串行更快；1 worker 更慢。不能用旧 Windows benchmark 的结果评价本次 Linux 代码是否变快或变慢，平台和测量口径不同。
- 轻任务三批中，1 worker 的中位数均比串行高；2 workers 相对串行加速比为 0.87、1.12、0.98，未展示稳定收益。
- 4 workers 的轻任务中位数在三批中均明显偏高：14.144、13.007、11.724 毫秒，且各批内部波动很大。复测 1 有一轮为 1.315 毫秒，说明不能概括为每轮都同样慢。现象重复出现，具体根因尚未定位。
- 任务包装、分配、队列同步、通知、调度和结果收集等工作可能影响轻任务收益，这是根据实现提出的解释方向，不是本次 profiling 证明的开销分解。
- 未采集上下文切换、锁等待、CPU 使用率、频率或温度；没有确认后台环境在各批之间完全一致，也未控制线程绑定和虚拟机调度。不能将 4 workers 的大幅变慢确定归因为某一因素。
- 本轮有限复测已足够记录现象，不要求持续重复直到得到加速结果。进一步定位属于后续可选实验。

## 学习过程与归属

本人按任务说明编写串行函数及主函数中的预热、五次测量、结果校验和中位数逻辑。助手审查发现并提示修正：`steady_clock::end()` 应为 `now()`；seed 应与线程池一致使用 `i + 1`；多余的右花括号提前结束 `main()`；串行输出需要标识。本人修改后完成 Linux Release 运行及两次轻任务复测。

2026-09-30 本人复述：轻任务下线程切换的代价可能使多线程没有更快；影响因素很多，没有单独测试锁竞争的影响，所以不能将四线程变慢直接归因于锁竞争。

助手反馈：第二点正确，已能区分观察到的现象与尚未验证的原因。第一点抓住了额外开销的方向，但解释不完整；助手补充，任务包装、内存分配、入队、加锁、唤醒、调度及 future 结果收集等开销可能超过并行计算节省的时间，线程切换只是候选因素之一，本次没有测量其具体贡献。不能把“线程切换代价高”作为已证实的根因。
